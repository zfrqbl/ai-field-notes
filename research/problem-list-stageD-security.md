## STAGE: SECURITY & ROBUSTNESS

### 1. Indirect prompt injection has gone operational: the open web is now an instruction-delivery channel for agents
- **Lifecycle stage:** Security (prompt injection)
- **Problem:** Indirect prompt injection (IPI) crossed from proof-of-concept to live exploitation in early 2026. Two independent telemetry sources (Google's security blog and Forcepoint X-Labs) concurrently confirmed adversaries seeding the open web with hidden instructions targeting browsing AI agents, coding assistants, and enterprise copilots; Palo Alto Unit 42 separately documented twelve detected IPI cases against AI agents (unit42.paloaltonetworks.com/ai-agent-prompt-injection, Mar 2026). The structural shift: browser agents click links and fill forms, coding assistants execute shell commands, CLI agents commit code and post to GitHub — each capability turned a formerly passive text-generation flaw into a path to unauthorized action. OWASP LLM01:2026 now defines prompt injection to include "retrieved content, tool output, image, audio, or video content, intermediate reasoning, or persistent memory"; MITRE ATLAS tracks it as AML.T0051 with Direct, Indirect and (since Nov 2025) Triggered sub-techniques. The attacker never talks to the model: they plant a payload where the model will read it later, and the instruction executes with the invoking user's privileges.
- **Evidence:** https://unit42.paloaltonetworks.com/ai-agent-prompt-injection · https://labs.cloudsecurityalliance.org/research/csa-research-note-indirect-prompt-injection-in-the-wild-2026 · https://www.stingrai.io/blog/prompt-injection-statistics-2026 (OWASP LLM01:2026 + MITRE ATLAS definitions, ASR data)
- **Ecosystem gap:** Agent frameworks treat fetched content as data, but models natively interpret anything in the context window as potentially authoritative; no framework marks untrusted content at ingestion time or scopes the actions a retrieved-instruction can trigger. The OWASP GenAI Q1 2026 round-up mapped eight major incidents (Jan-Apr 2026) to LLM and Agentic Top 10 items, and most trace to this single failure.
- **Solution sketch:** Treat all tool/fetch/retrieval output as untrusted data: delimit and label it in the prompt, strip instruction-like patterns before it enters context where cheap, refuse web-content-originated instructions for sensitive actions, and gate high-impact agent actions (shell, git push, external calls) behind human confirmation or a separate privilege scope. Monitor tool-call sequences for out-of-pattern actions (a browse agent suddenly writing files, a copilot calling new tools) as the runtime signal of a successful injection.
- **Difficulty:** Hard · **Priority:** 1 · **Zafar-backing:** Unknown — novel 2026 threat class; Zafar ships agents that browse/fetch, so exposure is plausible but unconfirmed.

### 2. MCP is the new trust boundary: tool poisoning, "rug-pull" tool descriptions, and the first real-world MCP supply-chain exploit
- **Lifecycle stage:** Security (MCP trust boundary)
- **Problem:** Every MCP server an agent connects to is potential exposure — tool descriptions, server responses, and metadata are all read by the model and can carry instructions it acts on. Microsoft documents Tool Poisoning: an attacker embeds malicious instructions inside MCP tool metadata (LLMs use descriptions to pick which tool to call), and in hosted-MCP scenarios tool definitions can be amended after approval — the "rug pull" — so a tool the user vetted changes underneath them. Supply-chain proof arrived in the wild: the npm package **postmark-mcp** (an MCP server for sending Postmark email) was tampered with to add a blind copy to an external domain, silently exfiltrating email contents — the first known real-world MCP server exploit. Cursor's agent-mode RCE was an earlier signal of what a malicious MCP server can do in an IDE with elevated permissions. On the wire, Unit 42 found MCP sampling (server→client model calls) rests on an implicit trust model with three new attack vectors, including server-injected instructions that persist across conversation turns.
- **Evidence:** https://developer.microsoft.com/blog/protecting-against-indirect-injection-attacks-mcp (tool poisoning, rug-pull) · https://labs.snyk.io/resources/prompt-injection-mcp (weaponizing benign MCP servers) · https://www.sysdig.com/learn-cloud-native/prompt-injection (postmark-mcp exploit, Cursor RCE) · https://unit42.paloaltonetworks.com/model-context-protocol-attack-vectors (MCP sampling attack vectors) · https://obot.ai/blog/mcp-prompt-injection-ai-agent-security (structural risk, layered defense)
- **Ecosystem gap:** MCP standardizes tool delivery but not tool trust: no signing/version pinning for tool definitions, no standard for scoping model capabilities per server, no audit log of what each server can see, and no registry vetting — so "more capabilities" adds attack surface as fast as it adds utility, and there is no `mcp doctor` equivalent for security posture.
- **Solution sketch:** Treat every non-vetted third-party MCP server as a possible trojan: pin server versions, review tool descriptions on install and on every update (rug-pull check), run servers with least-privilege credentials (scoped tokens, no blanket file/shell access), keep sampling disabled or fully mediated where not needed, and log which tool called what with which argument. Put security review of MCP servers on the same cadence as dependency updates.
- **Difficulty:** Medium · **Priority:** 1 · **Zafar-backing:** Unknown — plausible; agents + MCP-connected tooling is squarely his stack, but no personal incident confirmed.

### 3. Prompt-level defenses measurably fail; the mitigations that work are structural (tool filtering, design-level isolation)
- **Lifecycle stage:** Security (defense design)
- **Problem:** The instinctive fix — "tell the model in the system prompt to ignore instructions in tool output" — is measurably weak. In the AI Agent Red Teaming Challenge, indirect attacks showed higher average success than direct ones; measured defense results on gpt-4o-2024-05-13: a **tool filter** cut targeted attack success rate (ASR) from 47.69% to 6.84%, a prompt-injection **detector** cut ASR to 7.95% but dropped utility under attack to 21.14%, while **spotlighting + delimiting** barely moved ASR (41.65%). The design-level defense CaMeL solved 77% of AgentDojo tasks "with provable security" versus 84% for an undefended system (Debenedetti et al., arXiv:2503.18813). Independent analysis (obot.ai) reaches the same structural conclusion: MCP prompt injection cannot be fully solved at the agent level; the honest position is that no prompt-level mitigation is airtight.
- **Evidence:** https://www.stingrai.io/blog/prompt-injection-statistics-2026 (ASR measurements, tool-filter vs detector vs spotlighting, CaMeL/AgentDojo) · https://arxiv.org/abs/2503.18813 (CaMeL: provable security for LLM agent workflows) · https://obot.ai/blog/mcp-prompt-injection-ai-agent-security · https://www.practical-devsecops.com/mcp-security-vulnerabilities (MCPTox tool-poisoning benchmark; MCP preference manipulation attacks)
- **Ecosystem gap:** Defense guidance is still dominated by prompt-level advice ("add a security system prompt") that the data shows is the weakest lever; there is no standard, framework-level tool filtering / capability scoping primitive, and no mainstream benchmark that scores a defense on both security and retained utility (CaMeL's trade-off is the exception). Tool-poisoning prevalence is only now being quantified (MCPTox).
- **Solution sketch:** Design security in at the control plane, not the prompt: filter/retrieve the tool surface before each turn (fewer tools = smaller injection surface), scope each tool's privileges to least privilege, keep high-risk actions behind confirmation or a separate policy engine, log everything, and measure defenses on a paired security+utility benchmark rather than ASR alone. Use prompt-level guidance only as a cheap residual layer on top of structural controls.
- **Difficulty:** Hard · **Priority:** 1 · **Zafar-backing:** Unknown — engineering-trade-off content, plausible for the series' build/eval audience, unconfirmed.

### 4. Red-teaming agents is a different discipline from red-teaming chatbots: actions, not words
- **Lifecycle stage:** Security (evaluation / release gate)
- **Problem:** An agent red team tests actions, not only words. The categories that matter are prohibited actions, sensitive data leakage, task adherence, and indirect prompt injection arriving through the documents and tool results the agent reads (Microsoft's AI Red Teaming Agent names exactly these risk categories and tests cross-prompt injection / XPIA). Standard practice is converging: automated scanners (garak, Microsoft PyRIT, promptfoo, Foundry's AI Red Teaming Agent on PyRIT) run thousands of attacks and report an attack success rate, but Microsoft's own position is that automated tools must be combined with expert human analysis — automated scanners catch known patterns while creative multi-step attacks need humans. The OWASP Top 10 for LLM Applications (LLM01 prompt injection, LLM02 sensitive information disclosure, LLM05 improper output handling, LLM06 excessive agency) maps directly to CI/CD security activities with open-source tooling (promptfoo/garak for LLM01, Presidio for LLM02, ZAP/Semgrep for LLM05, Inspect AI/promptfoo for LLM06).
- **Evidence:** https://www.querynow.com/ai-agents/evaluation/red-teaming-ai-agents (actions-not-words categories, automated + human position) · https://devrev.ai/blog/ai-red-teaming (garak/PyRIT/promptfoo, OWASP/NIST/MITRE ATLAS mapping, agentic failure classes) · https://cybersecurity.cd.foundation/docs/ai/phase-2/ai-security-testing-and-red-teaming (OWASP LLM01-06 → CI/CD tool mapping) · https://github.com/requie/AI-Red-Teaming-Guide (40+ attack strategies, XPIA orchestrator, multi-turn)
- **Ecosystem gap:** Security testing for agents is still tacked onto the model-jailbreak playbook: agent-specific failure classes (excessive agency, tool abuse, data leakage via tool results, privilege escalation) have few standard test harnesses, and "red team actions not output" requires harnesses that can exercise and observe tool calls — most CI security tooling predates agentic systems.
- **Solution sketch:** Make agent red-teaming a release gate, not a launch-day exercise: run automated scanners (promptfoo / PyRIT / garak) against the agent's full tool surface in CI, add human red-team passes for multi-step attacks, score prohibited-actions, sensitive-data-leakage and task-adherence separately (not just refusal rate), keep a fixed regression attack suite that re-runs on every prompt/tool/model change, and map findings to OWASP LLM01-06 + MITRE ATLAS so fixes are classed, not ad hoc.
- **Difficulty:** Medium · **Priority:** 2 · **Zafar-backing:** Unknown — standard 2026 practice for shipping production agents; plausible, unconfirmed.
