# Agent Builder Log — Stage B problem list: BUILD & EVALUATION

Research window: 2026-11-23 → 2026-11-30 · compiled 2026-11-23
Scope: lifecycle stages (1) BUILD — agent orchestration, prompt engineering, tool calling, structured outputs, memory, context management — and (2) EVALUATION — evals, golden sets, regression testing, cost-aware evaluation, tracing.
Every item is URL-backed by at least one source observed in live search results (web_search/web_extract). No URLs or anecdotes invented. Zafar-backing marked "unknown" wherever not determinable; his personal experience is never assumed.

## 1. Tool-heavy agents pay ~70% input-token overhead just carrying tool schemas
- **Stage:** Build (tool calling, cost)
- **Problem:** In agents with many tools, the serialized tool definitions can cost more tokens per turn than the actual conversation. A tracked Hermes Agent issue reports ~70% input-token overhead on tool-heavy agents because the cached prefix (system + 3) skips the tools schema, so the whole schema is re-sent uncached every turn; a Reddit r/LLMDevs thread shows a team measuring tool definitions exceeding conversation tokens, with 20 tools sent every turn.
- **Evidence:** [Tool-heavy agents pay ~70% input-token overhead — `system_and_3` caching skips tools schema](https://github.com/NousResearch/hermes-agent/issues/20880) · [how are you handling tool token costs in agents with lots of tools? (r/LLMDevs)](https://www.reddit.com/r/LLMDevs/comments/1r6ga60/how_are_you_handling_tool_token_costs_in_agents/)
- **Gap:** Frameworks default to "send the full tool list every turn." There is no standard tool-selection layer, and prompt-cache breakpoints routinely exclude the tools schema, so the biggest static token block in the request is the least cached.
- **Fix sketch:** Add a cheap pre-pass (small/cheap model or deterministic router) that picks 2–3 of N tools per turn before the main agent call; reported ~70% reduction in tool-definition tokens. Also make cache breakpoints include the tool schema so it is written once and read per turn.
- **Difficulty:** medium · **Priority:** 2 · **Zafar-backed:** unknown

## 2. Subagent requests silently skip prompt caching — cached prefixes re-billed uncached
- **Stage:** Build (orchestration, cost)
- **Problem:** Anthropic's Claude Code/Agent SDK hardcodes `enablePromptCaching: false` for subagent internal queries while the main REPL defaults to true. Proxy logs from the issue's reporter show 54 subagent requests at ~7,000 tokens of identical tools+system prompt each, all billed uncached ≈ 378k wasted uncached input tokens per session. Companion Reddit thread (r/ClaudeAI, 121 points) documents the subscription-side analogue: sub-agent prompt caches live 5 minutes (vs 1h for the main conversation), so any tool call longer than 5 minutes expires the cache and the next request re-writes a few hundred thousand tokens at the expensive cache-write rate — eating the 5-hour usage window in an hour or two.
- **Evidence:** [Agent SDK subagents have prompt caching disabled by default (enablePromptCaching: false)](https://github.com/anthropics/claude-code/issues/29966) · [Sub-agents burning your Claude Code 5-hour window? Check their 5-minute prompt cache (r/ClaudeAI)](https://www.reddit.com/r/ClaudeAI/comments/1wj4gs0/subagents_burning_your_claude_code_5hour_window/)
- **Gap:** Caching policies are not uniform across the agent tree; a subagent is a first-class cost center that inherits none of the parent's cache settings, and short default TTIs are hostile to long-running tool calls.
- **Fix sketch:** Audit cache_control breakpoints on every request path (main, subagent, parallel). Set `"subagentPromptCacheTtl": "1h"` in settings where supported; in code, default subagent requests to the same caching path as the main model instead of `false`. Measure cache_read vs cache_create tokens per request class before and after.
- **Difficulty:** easy · **Priority:** 2 · **Zafar-backed:** unknown

## 3. Compaction/context-mutation rebuilds and tool-spec omissions break prompt-cache hits
- **Stage:** Build (context management, cost)
- **Problem:** Two independent cache-killer bugs with real measurement behind them: (a) Codex's local compaction request omits `tools`/`parallel_tool_calls` while every normal turn serializes them, so the compaction request's prefix never matches the session cache — on a ~235k-token session where normal turns ran 96–99% cached, each compaction re-billed ~235k uncached, adding ~70% to total uncached input; (b) Cline v4.1.25 broke Anthropic prompt caching on tool calls causing cost spikes, and Claude Code invalidates the cache when PreToolUse/PostToolUse `additionalContext` changes mid-history (22k-token prefix rewrites measured).
- **Evidence:** [Local compaction request omits tool specs, so it never hits the prompt cache (openai/codex #37305)](https://github.com/openai/codex/issues/37305) · [Broken Anthropic prompt caching on tool calls in v4.1.25 (cline #15307)](https://github.com/cline/cline/issues/15307) · [Prompt cache invalidated when PreToolUse/PostToolUse additionalContext changes during history rebuild (anthropics/claude-code #83913)](https://github.com/anthropics/claude-code/issues/83913)
- **Gap:** Prompt-cache correctness is an emergent property of every code path that touches the request prefix (compaction, hooks, dynamic tool state), but none of the frameworks test for it; prefix equality is silently assumed anywhere the serialized request is rebuilt.
- **Fix sketch:** Treat cache-breakpoint integrity as a testable contract: byte-compare the serialized prefix across turn types (normal / compaction / hook-injected), include `tools` in compaction requests (validated fix in codex #37305: 65–88% cached after), and pin hook-added context to the same position so the stable prefix survives.
- **Difficulty:** medium · **Priority:** 2 · **Zafar-backed:** unknown

## 4. Context compaction silently drops approvals, constraints and pending actions — the agent then acts against operator intent
- **Stage:** Build (context management, orchestration)
- **Problem:** A real incident (protoAgent ADR 0127): operator and agent agree a release plan; the chat auto-compacts; the summary keeps the operator's later "work is wrapped up" but drops the approval and the "merge on PASS" commitment. The agent then decides it had started the release without approval. The approval sat ~21K chars back in the replaced span behind ~30K chars of tool output, and each compaction can silently drop the previous compaction's summary. Research confirms the mechanism: context-compaction theory (arXiv 2608.01326) shows agent state after compaction diverges from the original conversation, and "Lost in Context Compaction" measured ~17% retention of side constraints through compactors vs >90% when constraints live in a separate store and are re-injected.
- **Evidence:** [ADR 0127 — Compaction fidelity (protoAgent)](https://protolabsai.github.io/protoAgent/adr/0127-compaction-fidelity.html) · [Context Compaction Theory (arXiv 2608.01326)](https://arxiv.org/abs/2608.01326)
- **Gap:** Compaction prompts are tuned for narrative summaries, not for preserving the few things that legally bind the agent: user approvals, standing instructions, pending scheduled actions. Frameworks provide no slot for "must never lose" facts.
- **Fix sketch:** Maintain a separate pinned store of commitments/approvals/pending actions re-injected every turn (protoAgent's `<working_state>` pattern), keep compaction prompts with explicit "restate verbatim" sections, and add a post-compaction loss test (probes for required facts + a behavioral check that the next decision is unchanged) before continuation.
- **Difficulty:** medium · **Priority:** 1 · **Zafar-backed:** unknown

## 5. Conversation summarization preserves narrative but loses the operational facts agents need to continue ("goldfish problem")
- **Stage:** Build (memory, context management)
- **Problem:** Sanity's engineering team documents that after one summarization pass useful details are gone; after three or four the agent "knows" you discussed authentication but cannot continue the work, and it has to grep everything again without knowing what to grep for. A measured walkthrough (Context Engineering loss tests) shows a plain summary keeps 1 of 6 required facts (roof ages 9 vs 22, rule R-ROOF-03, pending question Q-1004-01 all lost) and changes the next recommended decision from `escalate` to `approve`; a "pinned facts" block keeps 6/6 even at half the token budget. LLM summaries retain at most 16% of recurring details vs 79% for mechanical extraction (Compact-Bench).
- **Evidence:** [How we solved the agent memory problem (Sanity)](https://www.sanity.io/engineering/how-we-solved-the-agent-memory-problem) · [Compression, summarization and compaction, with loss tests (Context Engineering)](https://context.sammuthu.com/compaction/) · [Compact-Bench: Measuring What Context Compaction Costs Long-Horizon Coding Agents (arXiv 2610.31710)](https://arxiv.org/abs/2610.31710v2)
- **Gap:** The ecosystem's default memory strategy (summarize the window) optimizes for narrative coherence; agents need operational state — identifiers, numbers, open questions, versions — which fluent summaries smooth away.
- **Fix sketch:** Replace summarization with distillation: extract short narrative + verbatim fact lists ("this build reads env vars from SAM scripts, not Vercel"), pin facts that later steps depend on, and budget memory tokens strictly against task context. Treat "facts retained" as a measured eval, not an assumption.
- **Difficulty:** medium · **Priority:** 2 · **Zafar-backed:** unknown

## 6. Structured-output pipelines fail in ways validation and retry loops can't see: fences conceal violations, retries get the wrong error, uncapped loops bill-spike
- **Stage:** Build (structured outputs, prompt engineering)
- **Problem:** Large empirical study (3,997 attempts, 9 model/API configs) finds a 28.2% attempt-weighted schema-conformance failure rate driven by markdown-fenced JSON, and only 48% of fenced failures validate once the fence is stripped — a JSON parse error returned to the retry loop never names the length violation beneath the fence, so retries repair the wrapper and exhaust on a violation the loop was never told about (all 24 exhausted run-nodes ended on length_bound). Practitioner threads confirm the adjacent traps: retrying a truncation with the same max_tokens truncates again, uncapped retry loops turn one bad input into a bill spike, and a schemaless hallucinated enum value can survive 3 retries at temperature 0.
- **Evidence:** [Why Does Structured Output Fail? An Empirical Study of Prompt-Enforced Pydantic Schemas Across Nine LLMs (arXiv 2610.33949)](https://arxiv.org/abs/2610.33949) · [LLM Returns Invalid JSON Once in a While: Structured Outputs vs Validate-and-Retry (dev.to)](https://dev.to/libme/llm-returns-invalid-json-once-in-a-while-structured-outputs-vs-validate-and-retry-5faj) · [Retry Loops for LLM Validation Failures That Converge (The Prompt Bench)](https://thepromptbench.com/structured-outputs/retry-loops-for-validation-failures/)
- **Gap:** A single "validity rate" hides failure composition; providers' parse errors hide semantic violations; guidance on retry loops mostly says "retry" without classifying the failure, capping attempts, or formatting errors as model-actionable instructions.
- **Fix sketch:** Classify failures before fixing (truncation → raise max_tokens, re-check stop reason; fence → strip + revalidate and record residual; semantic → check against your own data, e.g. ID exists). Feed retry feedback as concrete instructions with the previous output in context, cap at 2–3 attempts with a defined fallback, and log retry rate as a metric (a prompt/schema/model change that moves it deserves an alert).
- **Difficulty:** medium · **Priority:** 2 · **Zafar-backed:** unknown

## 7. Agents copy tool answers verbatim — a wrong tool result propagates downstream as truth
- **Stage:** Build (tool calling, error propagation)
- **Problem:** A controlled evaluation (same model Claude Opus 5.5, 40 code-discovery questions, 4 setups) found agents treat whatever a tool returns as ground truth: when a tool classified a function *definition* as a *usage*, the agent copied the error into its answer; a function with 89 real call sites scored recall 0.54 with grep (agent filtered results itself) vs 1.00 when a tool handed over the answer list unchanged — perfect when the tool is right, fatal when it is wrong. The author's rule: "the agent copies the response verbatim, it treated whatever answer the tool gave it as the truth."
- **Evidence:** [Agents Take Your Tool's Answer Literally (Erik Perttu)](https://dontcodethisathome.com/agents-take-your-tools-answer-literally)
- **Gap:** Tool-output trust is binary in most harnesses; nothing scores tool-result confidence or tells the agent which parts of a tool answer are sourced vs inferred, so wrong tool output infects every downstream stage.
- **Fix sketch:** Evaluate tool instructions/outputs before keeping them (measure tool precision, not just agent end-to-end score); design multi-stage pipelines assuming an earlier stage can be wrong — have the consuming stage verify high-stakes claims (definition ≠ usage, ids exist) or cite the exact tool line; surface tool provenance so downstream steps can weigh it.
- **Difficulty:** medium · **Priority:** 3 · **Zafar-backed:** unknown

## 8. Agents loop on identical failing tool calls with no convergence detection — budgets burn without progress
- **Stage:** Build (orchestration, tool calling)
- **Problem:** "Agent loop non-termination" ranks #2 (~8 issues) in a ~200-bug classification of the Claude Code tracker: the model calls a tool, it fails, and it retries the identical call — an explore agent re-reading a 41K-token file and hitting the same `MaxFileReadTokenExceededError`, repeated identical Edit failures, a Playwright SQL-injection loop. Same pattern independent of vendor: OpenClaw logs an edit tool rejecting an identical patch ("No changes made") 20+ times, and Hermes Agent's stall fix enumerates the read-check loop and same-error retry cycle. The generate loops check step count and token budget but not "same call repeated N times" or "no progress between rounds".
- **Evidence:** [Agent loop non-termination: model retries identical failing tool calls indefinitely (anthropics/claude-code #30150)](https://github.com/anthropics/claude-code/issues/30150) · [Runtime safety: break out of repeated identical failed tool calls (openclaw #86454)](https://github.com/openclaw/openclaw/issues/86454) · [feat(agent): add stall detector to stop repeated tool calls (NousResearch/hermes-agent #41477)](https://github.com/NousResearch/hermes-agent/issues/41477/linked_closing_reference?reference_location=REPO_ISSUES_INDEX)
- **Gap:** Agent runtimes treat budget caps as termination, but a loop that converges on nothing is invisible to max-iterations checks; no standard, framework-level convergence detector exists.
- **Fix sketch:** Add a stall detector keyed on canonical (tool_name + arg-hash) signatures: warn after N identical consecutive calls (inject "try a different approach" as a system message), hard-stop after a threshold, optionally remove the blocked tool from the visible set for the session; treat loop guardrails as one of the four essential stop conditions of any harness.
- **Difficulty:** medium · **Priority:** 2 · **Zafar-backed:** unknown

## 9. Exact-match assertions on tool calls produce ~half false failures — and a broken metric poisons the team
- **Stage:** Evaluation (tool-call evals)
- **Problem:** A team's dashboard showed 22% tool-call failures for a quarter; every fix (better descriptions, stricter schema, planning-model swap) moved the number 20→24→22. A manual audit of 100 failures found 47 were correct calls the assertion scored wrong: equivalent encodings ("2026-03" vs "2026-03-01", cents vs dollars), argument ordering (a set compared as an ordered list), explicit defaults, and different-but-valid paths (get_customer instead of search_invoices). True rate ≈11.7%. Worse, exact match also false-passes: in 11 of 120 green runs the agent repeated a *correct* call for a step that shouldn't have happened (looping) — "a bad trajectory made of good tool calls". The human cost compounded: engineers stopped triaging a dashboard half of whose failures were noise. Inversely, a hand-written normalizer created a fake *pass* (an ISO timestamp named a February moment while `str(v)[:7]` compared it as March).
- **Evidence:** [Nearly half our agent's tool-call failures were our assertion, not our agent (dev.to)](https://dev.to/james_oconnor_dev/nearly-half-our-agents-tool-call-failures-were-our-assertion-not-our-agent-1p59)
- **Gap:** Eval frameworks ship "expected tool + expected args, dict compare" as the canonical case, which only works for 4 tools with one encoding per field; nobody measures the eval's own false-failure and false-pass rate.
- **Fix sketch:** Normalize before comparing (canonical encodings, sets vs lists, defaults), and validate the normalizer against effect assertions so a rule removing false failures can't create false passes. Grade trajectories, not isolated calls — per-call grading certifies steps a trajectory view would fail. Read 100 failures by hand before trusting any tool-call metric.
- **Difficulty:** medium · **Priority:** 1 · **Zafar-backed:** unknown

## 10. Final-answer evals pass while the trajectory fails — the SQLite problem
- **Stage:** Evaluation (trajectory evals)
- **Problem:** "The Eval That Passed Wrongly": an experiment designed to evaluate a vector database passed end-to-end while the trajectory showed the agent gave up on the database and silently used SQLite for the same task — "every thing worked, and the whole measurement was wrong because it was looking at the wrong product surface completely." Arize's benchmark amplifies: 7 models × 19 GitHub-ops tasks × 10 runs kept correctness in a tight 79.6–85.1% band while latency, tool-call counts, retries and timeout risk moved far more — an output judge can pass a polished summary while the requested action never happened (stale data queried, invalid arg passed, completion claimed without verifying the update). A LinkedIn report mirrors it: green eval suite at ship, confidently wrong in production two weeks later.
- **Evidence:** [Why Agents Need Custom Evals and How to Create Them — The Eval That Passed Wrongly (Testμ 2026)](https://www.testmuai.com/blog/custom-agent-benchmark-trajectories-frictions/) · [How to Debug Agent Failures Your Evals Are Missing (Arize)](https://arize.com/blog/how-to-find-and-debug-agent-failures-your-evals-are-missing/) · [We shipped with a green eval suite. Two weeks later the system was confidently wrong in production (LinkedIn)](https://www.linkedin.com/posts/kunal-phadnis_online-vs-offline-evaluation-in-ai-2026-activity-7501351525081067521-NcLZ)
- **Gap:** Evaluators default to scoring the final answer; the trajectory (tool calls, retries, state changes, the bypassed tool) is the actual product surface and is almost never asserted on. Offline suites can't anticipate live inputs, and no standard dataset seeds offline tests from production traces.
- **Fix sketch:** Add trajectory-level evaluators: assert the intended tool was used (not a substitute), the state change happened (code evaluator on observable outcome), cost/latency/retry bounds per task; convert every confirmed production failure into a regression fixture and gate releases on both offline evals and monitored online quality.
- **Difficulty:** medium · **Priority:** 2 · **Zafar-backed:** unknown

## 11. Reference-heuristic and LLM-judge scoring miss fabricated tool use — deterministic validators change the conclusions
- **Stage:** Evaluation (tool-call evals, judges)
- **Problem:** Re-scoring 33,583 traces from 13 agents against a deterministic validator (checks tools called, executed params, resulting state, answer values supported by real tool observations) flips results: Gemini-2.0-Flash scores 63.4% under substring heuristic vs 5.6% under the validator. In a paired experiment, injecting one schema-valid wrong argument into the first tool call raised errors from 52.4% to 74.5% — an LLM-judge ensemble estimated only +2.5 points on the same pairs, i.e. judges don't see it. Agents also *report tool results without executing any call* in 0–42.5% of traces (model-dependent) because the harness accepts an action and a final answer in one completion.
- **Evidence:** [Measuring What Tool-Using LLM Agents Actually Do: Structured Validation, Causal Error Propagation, and Fabricated Tool Use (arXiv 2604.16706)](https://arxiv.org/html/2604.16706v3)
- **Gap:** The default eval stack (reference string match or LLM judge) is calibrated on final answers, so correctness-by-construction failures — fabricated tool calls, wrong-but-valid arguments — get scored as successes; judges are expensive and blind to exactly the failures that matter.
- **Fix sketch:** Where any tool state is involved, replace/augment answer scoring with a deterministic validator over the execution trace; enforce that a tool *observation* precedes any claim about it (reject answer-without-execution at the harness level); add runtime monitors (the paper's is ~7µs/trace) that abstain rather than guess.
- **Difficulty:** hard · **Priority:** 1 · **Zafar-backed:** unknown

## 12. Eval suites rot: brittle assertions, tutorial-written tests, and blind spots shared with the model
- **Stage:** Evaluation (eval hygiene)
- **Problem:** The "Eval Smell Catalog" audits a suite with 847 cases, six months of 94% green, and a summarization feature confidently wrong ~1-in-20 in production. Catalogued smells: brittle exact-match against natural language (no canonical surface form; every model upgrade reshuffles phrasing), suites written like tutorials (measure instruction-following, not problem-solving), tests run against one or two agents whose quirks get encoded into the product, and pass/fail collapses hiding wrong docs, deprecated endpoints and dozens of tool calls behind green.
- **Evidence:** [The Eval Smell Catalog: Anti-Patterns That Make Your LLM Eval Suite Worse Than No Evals At All](https://tianpan.co/blog/2026/04/16/eval-smell-catalog-llm-testing-antipatterns) · [LLM Evals: What Runs After You Edit a Prompt (Beagle)](https://www.heybeagle.com/blog/llm-evals-what-runs-after-you-edit-a-prompt)
- **Gap:** Eval maintenance is unowned work — nobody treats the eval suite itself as a system that needs upkeep, and the failure modes of tests (which the classic test-smell literature named decades ago) are rediscovered per-team in LLM form.
- **Fix sketch:** Use extract-and-normalize or property assertions for free-form output, exact match only where format is the point (SQL, tool call, enum); run evals per component (tool selection, retrieval) as well as end-to-end so regressions are localizable; audit suites periodically — a green dashboard with zero human triage is a liability, not a signal.
- **Difficulty:** easy · **Priority:** 2 · **Zafar-backed:** unknown

## 13. Observability without evals: 89% of teams watch, 52% can judge — traces never become regression tests
- **Stage:** Evaluation (tracing → regression)
- **Problem:** LangChain's State of Agent Engineering survey (1,340 respondents): 89% of teams have observability instrumented, but only 52% run offline evals and 37% online — a 37-point gap that holds across company sizes. Observability answers *what happened* (which model, which tool, how many tokens); evals answer *was it right*, and "right" lives inside the workflow (a reconciliation entry posted to the wrong account is a successful tool call in the trace). The cost curves diverge: sampling scales with traffic, judging scales with the number of business rules, which is human time and never a switch.
- **Evidence:** [LLM observability & monitoring: how to evaluate agent behavior (LangChain)](https://www.langchain.com/resources/llm-monitoring-observability) · [The agent observability gap: 89% watch, 52% eval (OOMeta)](https://oometa.ai/en/insights/agent-eval-observability-gap-2026)
- **Gap:** Trace storage is a solved commercial problem; the trace→dataset→eval handoff (find failing trace, preserve it as a fixture, write expected behavior, re-run on every change) is manual work in every tool, so production failures evaporate instead of becoming regression coverage.
- **Fix sketch:** Close the loop mechanically: on every confirmed failure, add the trace to a dataset with recorded expected behavior, then re-run that dataset against every prompt/tool/model change before release (ServiceNow's golden-dataset-from-successful-runs pattern); keep traces and eval scores attached so a low score links to the run that earned it.
- **Difficulty:** medium · **Priority:** 2 · **Zafar-backed:** unknown

## 14. Cost and latency are outside eval scope — loops and context growth silently multiply spend per run
- **Stage:** Evaluation (cost-aware evaluation)
- **Problem:** Agent cost compounds per node, and dashboards report aggregates: a six-agent extraction run costing ~41,000 input tokens looks unremarkable until span attribution shows the retriever alone passing 120 chunks into context (~27,600 tokens, two-thirds of the bill); reranking to 15 chunks cuts the run ~63% (from 12¢ to 5¢ per run, ≈$283k/yr at 10k runs/day). Each loop iteration adds tokens to the window, so three extra iterations cost more than projected and nothing flags it. Correctness bands can look identical while cost/latency/retry exposure varies wildly (Arize's 7-model benchmark).
- **Evidence:** [Multi-Agent Observability: Tracing Agents in Production (Cognilium)](https://cognilium.ai/blogs/multi-agent-observability) · [AI Agent Monitoring: Why Traditional APM Falls Short (LangChain)](https://www.langchain.com/resources/ai-agent-monitoring)
- **Gap:** Standard eval harnesses compare correctness only; cost per accepted result, per-step token attribution, retry rate and latency are treated as ops metrics, so a change that doubles spend at equal quality ships green.
- **Fix sketch:** Make cost/latency first-class eval outputs: attribute tokens per span, gate releases on cost-per-accepted-inference bounds, alert on cost-per-run rising (loop, oversized context, model swap) and retry-rate rising (flaky tool, malformed schema), and sample trajectories structurally — keep 100% of failures/escalations, ~10% of healthy runs, not random samples.
- **Difficulty:** medium · **Priority:** 2 · **Zafar-backed:** unknown

## 15. Scalar benchmark scores don't transfer: evals are evidence about a particular evaluation, not a verdict on the model
- **Stage:** Evaluation (benchmarks, model selection)
- **Problem:** Ai Engineer's talk "Evals Are Broken, Use Them Anyway" opens with GPT-5.4 and Gemini 3.1 Pro Preview sitting side-by-side on a benchmark dashboard with near-identical scores and behaving differently in use: a scalar score makes models look interchangeable and conceals substantial differences. The claim is not to abandon measurement — abandoning measurement creates the opposite problem — but to treat dashboard numbers as evidence about a specific evaluation, never a complete description of either model. SAAG (arXiv 2607.18245) makes the same point at call level: exact-match collapse hides whether a model selected the right function but hallucinated arguments, or satisfied the schema for the wrong reason.
- **Evidence:** [Evals Are Broken, Use Them Anyway (ai.engineer)](https://ai.engineer/talks/QuuIywMG4s8-evals-are-broken-use-them-anyway) · [SAAG: Structured Agent Assessment and Grounding (arXiv 2607.18245)](https://arxiv.org/html/2607.18245)
- **Gap:** Teams pick models and prompts off single composite numbers, and vendors optimize leaderboards — there is no standard decomposition of agent-call failures (registry conformance vs structural completeness vs argument grounding) to make scores actionable.
- **Fix Sketch:** Build your acceptance eval on *your* tasks and read scores as distributions with failure composition, not ranks; use stage-decomposed diagnostics (which stage of the call failed) so a score drop tells you what to fix; keep a small human-reviewed calibration set to check the scorer reflects what users value.
- **Difficulty:** hard · **Priority:** 3 · **Zafar-backed:** unknown

## 16. LLM-assisted golden datasets embed subtly wrong examples — a green suite can't tell you the ground truth is bad
- **Stage:** Evaluation (golden sets, regression testing)
- **Problem:** A field post (AdQuick AI Copilot, 53 tools): golden datasets built with LLM-assisted examples were fast to produce, but LLMs generate subtly wrong examples too — after an automated nightly eval-and-fix loop improved most tools, three tools stayed at exactly 0% score. "That shouldn't happen. Even broken tools improve slightly when prompts get better. Zero movement meant one thing: the training examples themselves were wrong." Fixing the three examples jumped the suite past 80%.
- **Evidence:** [I built a self-healing eval system that fixes itself overnight (Aviral Singh, LinkedIn)](https://www.linkedin.com/posts/zoosphar_ibuilt-a-self-healing-eval-system-that-fixes-activity-7462343793359470592-HS7I)
- **Gap:** Golden-set generation and curation are treated as one-time scaffolding work; nothing measures *dataset* quality (LLM-judge score on top of LLM-derived labels compounds both LLMs' blind spots), and there is no standard "zero-movement" heuristic for detecting poisoned fixtures.
- **Fix sketch:** Treat golden datasets as code with review and versioning: audit LLM-generated examples before they enter the set, use invariants (correct tools must improve at least a little under any real prompt fix — zero movement across a suite of fixes is a dataset bug, not a model bug), and refresh fixtures from confirmed production traces rather than synthetic generation alone.
- **Difficulty:** medium · **Priority:** 3 · **Zafar-backed:** unknown
